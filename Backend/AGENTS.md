# Backend 開發代理規範

本文件適用於 `Backend/` 及其所有子目錄。修改此範圍內的程式碼時，必須遵守以下規範；若更深層目錄另有 `AGENTS.md`，則以較深層文件的補充或覆寫規則為準。

## 專案概況

- 語言：Python 3。
- Web 框架：FastAPI。
- 資料庫：SQLite。
- 測試框架：優先沿用標準函式庫 `unittest`。
- 路徑操作統一使用 `pathlib.Path`，避免混用裸字串與平台限定的路徑拼接。
- 對外文字、錯誤訊息與文件以繁體中文為主；既有公開介面的名稱若為英文，不任意更名。

## 核心設計原則

### 函式原子化

- 每個函式只負責一件可清楚命名、可獨立驗證的事情。
- 將「取得資料、解析資料、驗證資料、轉換資料、保存資料、輸出訊息」拆成不同函式；流程函式只負責編排這些小函式。
- 優先撰寫無副作用的純函式。檔案、網路、資料庫、環境變數與終端輸出等副作用必須集中在邊界函式，不得隱藏在看似只做計算的函式中。
- 函式若同時出現多個獨立階段、需要使用「以及／然後」才能描述其職責，或必須大量註解才能區分區塊，應考慮拆分。
- 不為了追求極短函式而拆出只包裝單一運算、沒有語意且不會複用的函式。原子化以「單一職責、清楚契約、可測試」為準，不以行數為唯一判準。
- 優先使用提早返回降低巢狀層級；避免過長函式、過多布林旗標及難以追蹤的隱性狀態。

### 優先複用

- 新增函式前，先搜尋同一模組、相鄰模組及整個 `Backend/` 是否已有相同或相近能力。
- 相同邏輯出現第二次時，優先抽取為共用函式；僅有名稱不同但行為相同時，以參數化取代複製。
- 共用函式應放在最接近其業務語意的模組。只有跨多個業務領域且不依賴特定領域時，才放入 `util/`。
- 不建立籠統的 `helpers.py` 或萬用工具類別。模組與函式名稱必須表達用途。
- 保留既有公開介面時，可用薄包裝函式維持相容性，但核心邏輯只能有一份，並在文件中說明其相容性用途。
- 不因複用而過早建立複雜抽象。抽取後的介面必須比重複實作更容易理解、測試與維護。

## 函式文件契約

每個新建或實質修改的函式與方法，都必須使用繁體中文 docstring，明確包含下列三個標題：

1. `輸入契約`：參數型別、允許值、必要前置條件，以及 `None`、空值、路徑或資源狀態的約束。
2. `函式效果`：執行內容，以及可能發生的檔案、網路、資料庫、日誌或狀態變更等副作用；純函式也應明示不產生副作用。
3. `輸出結果`：回傳型別與語意；若可能拋出例外，列出可預期的例外類型及觸發條件。

統一格式如下：

```python
def normalize_case_number(case_number: str) -> str:
    """正規化案件編號。

    輸入契約：
        case_number 必須是非空白字串，可包含前後空白。
    函式效果：
        移除前後空白並統一英文字母大小寫；不修改外部狀態。
    輸出結果：
        回傳正規化後的案件編號字串；輸入為空白時拋出 ValueError。
    """
```

- 簡單的 `lambda`、型別別名與無行為的資料欄位不需要 docstring。
- 覆寫框架或父類別方法時，若契約完全一致可引用父類別契約；只要行為或限制不同，就必須完整記錄差異。
- docstring 必須描述可觀察的契約，不得只是重述函式名稱或逐行翻譯實作。
- 型別註記不可由 docstring 取代；公開函式的參數與回傳值必須同時具備完整型別註記。

## 程式碼規範

- 使用具體且能表達領域意義的英文識別名稱；避免不明縮寫、單字母變數與名稱不符行為。
- 常數使用 `UPPER_SNAKE_CASE`，函式與變數使用 `snake_case`，類別使用 `PascalCase`。
- 優先使用標準函式庫與既有依賴；新增第三方套件前必須確認現有工具無法合理完成需求。
- 例外處理應捕捉可合理處理的具體例外，不使用裸 `except`，也不得靜默吞掉錯誤。
- 錯誤訊息應包含足以定位問題的上下文，但不得洩漏密碼、權杖、個資或完整敏感文件內容。
- 資料庫的多步驟寫入應置於同一交易；失敗時必須回滾，連線與檔案等資源必須確實關閉。
- 外部輸入一律在邊界驗證。ZIP 路徑、檔名、URL、SQL 來源及使用者輸入不得直接信任。
- 不在 import 階段執行網路、資料庫寫入或輸出訊息等副作用。

## 測試要求

- 新功能與錯誤修正必須新增或更新測試；優先直接測試原子函式，再測試流程整合。
- 每個公開函式至少涵蓋正常路徑、重要邊界值，以及契約中列出的主要失敗情境。
- 網路、時間、檔案系統外部狀態及資料庫邊界應以暫存資源或 mock 隔離，測試不得依賴正式服務與固定的本機狀態。
- 修正缺陷時，先加入能重現問題的回歸測試，再修改實作。
- 測試名稱應清楚表達情境與預期結果，且測試彼此獨立、可重複執行。

在專案根目錄執行：

```powershell
python -m unittest discover -s Backend/test -p "test_*.py"
```

## 修改流程與完成標準

1. 先閱讀相關模組與測試，並以搜尋確認是否已有可複用的實作。
2. 確認輸入、輸出、副作用與錯誤契約，再決定函式邊界。
3. 以最小範圍修改，避免順帶重構無關程式或破壞既有公開介面。
4. 為新增或修改的行為補上中文契約 docstring 與對應測試。
5. 執行相關測試；若變更影響共用程式，再執行完整測試套件。
6. 完成前檢查：無重複邏輯、函式維持單一職責、型別註記完整、資源已關閉、例外未被吞掉，且未提交機密或產生檔。

只有在實作、文件與測試一致，且所有可執行的相關測試通過後，工作才視為完成。若因環境限制無法執行測試，必須明確說明未驗證項目與原因。
